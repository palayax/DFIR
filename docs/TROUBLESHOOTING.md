# Troubleshooting

Symptom → cause → fix, drawn from issues actually documented and reproduced in this repository (`RUN_LOG.md`, `config/irtriage.yaml`'s own warning comments, and the source files cited). Nothing below is speculative.

---

## Client (`IRTriage.exe`)

| Symptom | Cause | Fix |
|---|---|---|
| Double-clicking `IRTriage.exe` does nothing, or every flag (even `--help`) fails immediately, no output at all | The EXE carries an embedded `requireAdministrator` PE manifest; Windows' loader enforces it *before* any Go code runs, for every invocation, not just ones that need privileged access | Right-click → **Run as Administrator**. If you must run it from an already-privileged but non-manifest-aware caller/test harness, set `__COMPAT_LAYER=RunAsInvoker` in that process's environment before launching it (this is a test-harness technique — see `scripts/smoke-client.sh` — not a normal operator workflow) |
| A real run appears to hang or crash with exit code 2 shortly after starting, specifically after changing `run.memory_limit_mb` from the shipped default | Forwarding this value as Velociraptor's `--hard_memory_limit` triggers a nil-pointer panic inside Velociraptor v0.77.2 itself (`executor/nanny.go:92`, reached via `bin/artifacts.go:302`) — reproduced empirically: baseline + `--timeout`/`--cpu_limit`/`--progress_timeout` alone are fine; adding `--hard_memory_limit` alone crashes every artifact | This build never emits `--hard_memory_limit` to Velociraptor regardless of the config value, so this should not occur with an unmodified build. If you see it, check `advanced.velociraptor_extra_flags` for a manually-added `--hard_memory_limit`/equivalent and remove it. Do not attempt to re-add memory limiting via `velociraptor_extra_flags` until the upstream Velociraptor bug is fixed |
| YARA detections look far sparser than expected — files you know match multiple rules only ever produce one detection row | `rules.yara.number_of_hits` was changed from its default of `1`. Any value other than `1` (`3`, `5`, `50`, ...) collapses Velociraptor's `yara()` VQL plugin output to a single row per file (first matching rule only), discarding every other rule that also matched — this is a Velociraptor semantic, not a bug in this tool | Set `rules.yara.number_of_hits: 1` (the shipped default). See the full warning in `config/irtriage.yaml` and in [`CONFIG_REFERENCE.md`](CONFIG_REFERENCE.md#rulesyara) |
| Set `rules.nuclei.allow_network: true` expecting network/DAST templates to run, but nothing changed and a warning about "no effect" appears | `Custom.IRTriage.Nuclei.Files` hardcodes `-pt file -file` unconditionally in its own VQL; `client/internal/rules/nuclei.go`'s `nucleiFileCategories()` structurally refuses any template category that isn't exactly `file` or `file/*`, and non-file categories are not even embedded in the binary at build time | This is expected, permanent behavior for this build — network scanning from this tool is not implemented, regardless of config. Do not rely on this flag; if you need network/DAST scanning, use a separate tool outside this pipeline |
| `--dry-run`, `--list-artifacts`, or a real run all fail immediately with an error mentioning missing or placeholder payloads | `client/embedded/` still holds `build/build.ps1`'s committed **placeholder** payloads (a fresh checkout, or a build that hasn't staged real assets yet) — `internal/assets`' `Verify()` fails by design rather than silently running with fake binaries | Run `build/build.ps1` (without `-SkipFetch`, at least once) to fetch and stage real payloads. Check `client/embedded/manifest.json`'s `placeholder` flags per payload to confirm real staging occurred |
| `--validate-config` (or any real run) fails with an error naming an unrecognized config key | Config parsing is strict (`KnownFields(true)`): any key not in the schema — commonly a typo, or a key from a different/older version of `irtriage.yaml` — is a hard error, not a warning | Fix the key name. Compare against the shipped `config/irtriage.yaml` and [`CONFIG_REFERENCE.md`](CONFIG_REFERENCE.md) for the exact key set. This is deliberate: a silently-ignored typo that disables a collector is unacceptable in a forensics tool |
| Run started with `run.profile: custom` fails validation immediately with no collection attempted | `profiles.custom.velociraptor_artifacts` and `native_collectors` are both empty — the shipped default. A custom profile must not silently collect nothing | List at least one artifact or native collector under `profiles.custom` in your config. See the worked example in [`CONFIG_REFERENCE.md`](CONFIG_REFERENCE.md#5-custom-profile--event-logs-and-registry-only-no-file-walk) |
| `--allow-unelevated` run completes, but scheduled tasks, raw volume data, other users' registry hives, other processes' memory, or the Security event-log channel are missing/empty in the output, while everything else looks fine | These specifically require true administrator elevation. `--allow-unelevated` lets the run proceed without it, and the affected collectors are skipped with a logged warning rather than aborting the whole run | This is expected, documented reduced coverage, not a bug. Re-run elevated (no `--allow-unelevated`) if you need this data. `manifest.json` in the output records exactly which collectors were skipped and why |
| `--decrypt` fails immediately, or fails partway with no output file written | Wrong `--password`, or the input file is not a valid `IRTAESV1` container (e.g. it's the plain unencrypted `.zip`, or it's truncated/corrupted) — GCM authentication fails on the very first chunk before any plaintext is written | Confirm you're pointing at the `.zip.aes` file and using the exact password set in `output.zip_password` at collection time. A failed decrypt never leaves a partial file at the destination — check the error text for which chunk failed authentication |
| `--verify` reports `MISMATCH` or `MISSING` for one or more files | The archive was modified, partially copied, or corrupted after collection (or, for `MISMATCH`, a hash algorithm mismatch between what `SHA256SUMS` recorded and what's present) | Treat this as a chain-of-custody failure — re-obtain the archive from its original source. Do not treat a `MISSING`/`MISMATCH` result as cosmetic |
| The `full` profile collected **0 raw evidence files** (`files collected: 0 (0 bytes)`) while `basic` on the same host collected some, even though `full` searches a superset of globs | `full` ships `file_collection.accessor: ntfs`, which parses the raw NTFS volume via `\\.\C:` and needs an elevated token. Unelevated it does **not** error — it matches zero files. Measured unelevated on the build host: `basic` (accessor `auto`) 13 globs → 15 files / 4,903,936 bytes; `full` (accessor `ntfs`) 30 globs → 0 files. So the more thorough profile collected strictly less | Re-run elevated — `ntfs` is genuinely better there (locked files, deleted entries). If you must run unelevated, set `profiles.full.file_collection.accessor: auto` to use the Windows API instead. Since 2026-09-29 the run logs an explicit warning naming this cause and fix before the collection starts; `Generic.Collectors.File` also appears in `manifest.json`'s `coverage.empty[]` |
| `manifest.json`'s `memory.runs[]` reports `status: "failed"`, `error: "dump_produced_0_bytes"` for `Windows.Memory.ProcessDump:lsass.exe`, on a run that *was* elevated | lsass is running as a **Protected Process Light** (LSA protection / `RunAsPPL`, on by default on Windows 11 and on any machine with Credential Guard). PPL denies `MiniDumpWriteDump` even to SYSTEM, so the artifact opens its output, writes nothing, and still exits 0. Elevation is not the missing ingredient — **re-running as Administrator will not help** | Confirm with `reg query HKLM\SYSTEM\CurrentControlSet\Control\Lsa /v RunAsPPL` (`0x1`/`0x2` = protected). If it is enabled, acquire a full physical-memory image instead (`memory.full_memory_dump: true`, elevated, and budget the disk — it writes roughly RAM-sized) and carve lsass out of it offline. Do **not** disable PPL on a live host during an incident: it is a reboot-persistent security downgrade on a machine you are still investigating |
| `memory.runs[]` reports `status: "failed"`, `error: "dump_file_not_produced"` | The artifact ran and exited 0 but uploaded no file at all — a different failure from the 0-byte case above. Usually the process name did not match any live process (`process_names` is matched anchored and case-insensitively against `pslist()`'s `Name` column, so `lsass` will not match `lsass.exe`), or the process exited between enumeration and dump | Check the spelling in `memory.process_names` against `manifest.json`'s own process list or `Windows.System.Pslist` output in `raw/`. The name must include the `.exe` suffix |
| `memory.runs[]` reports `status: "ok"` but the target's `dump_bytes` is `0` | Should not happen — a 0-byte dump is demoted to `failed`. If you see it, the run predates 2026-09-29 (when `status` alone was not trustworthy: an elevated run recorded `ok` for a PPL-blocked lsass dump of exactly zero bytes) | Trust `dump_bytes`, not `status`, on older archives: `dump_bytes: 0` on a non-skipped run means no memory was captured whatever the status says. That is precisely why the byte count is published alongside the verdict rather than only used to compute it |
| A build with `-SkipTests` or a modified `client/internal/rules` package fails `go test` with a `*_Prepare_MissingPayloadIsGraceful` failure right after staging real payloads | These tests assert graceful failure against a **placeholder** manifest; once real payloads are staged, `Prepare()` legitimately succeeds, which is a different (correct) code path than what the test names assume. This is why `build/build.ps1` deliberately runs the Gates step (including `go test`) **before** the Stage-payloads step | Do not reorder the build's own steps. If you're modifying the build script itself, keep Gates before Stage payloads, or update these tests to check the manifest's actual payload state instead of assuming placeholders |

## Web app

| Symptom | Cause | Fix |
|---|---|---|
| Every file you add on **Ingest** immediately shows `error: ingest worker unavailable`, though the page itself rendered fine | Fixed on 2026-09-29; if you see it, you are running a build from before that. `new Worker(...)` throws when the app is opened from `file://` (browsers refuse a module worker from an opaque origin) or when the worker URL resolves cross-origin, and the old code treated that as a terminal error for every file — making the whole app unusable while looking healthy | Update to a current build, which falls back to parsing on the main thread and says so via a one-time toast. As a workaround on an old build, serve the app over HTTP (`python -m http.server`) instead of opening it from disk |
| Ingesting a large file from `file://` makes the tab unresponsive for several seconds, but works | Expected. From an opaque origin there is no Web Worker, so parsing runs on the main thread. A one-time toast says so | Serve the app over HTTP if you need the UI to stay responsive while a multi-hundred-MB acquisition parses |
| Analysis fails immediately with a credentials error | The selected LLM provider's required fields are incomplete — see the exact list per provider in [`WEB_APP.md`](WEB_APP.md#41-llm-providers) | Fill in every required field for that provider. Use the mock provider (no credentials needed) to confirm the rest of the pipeline works before configuring a real provider |
| Vertex-mode Google provider analysis fails partway through a long session with an authentication error, having worked earlier in the same session | `accessToken` for Vertex mode is a short-lived OAuth bearer token; this app implements no refresh flow — you are responsible for supplying a live token | Obtain a fresh access token and re-enter it. There is no "expired, auto-refreshed" state to wait out |
| Export to Google Cloud Storage has no "get a shareable link" / presigned-URL option, unlike Azure Blob or S3 | GCS V4 signed URLs require RSA private-key signing tied to a service account — a different, out-of-scope crypto flow from the OAuth bearer token this adapter uses. `presignedUrl()` is simply not implemented for this provider (it's optional on the `StorageProvider` interface) | Use `bucket`/object path plus your own GCS console or `gsutil` access to share the object, or export to local download / a different provider instead |
| Export to local storage, then an attempt to "load it back" from the same provider fails | The local storage adapter is a one-way download sink (`showSaveFilePicker` or a synthetic `<a download>` click) — `get()`/`list()`/`delete()` all throw deliberately | Re-ingest the downloaded file through the normal **Ingest** step instead of expecting the storage provider to serve it back |
| Analysis produces a report where `dashboard`/`scope`/`mitre_coverage` don't match what you expected the model to say | This is by design, not a bug: those three sections are always overwritten with deterministically-computed values in the pipeline's assemble stage, and the model's own output for those specific keys is discarded unconditionally | If the deterministic values look wrong, the underlying merged SuperTimeline data is the thing to check, not the prompt — these fields never come from the model |
| A model call returns something that fails validation more than twice in a row and the pipeline gives up | `DEFAULT_MAX_REPAIR_ATTEMPTS = 2` — after the model fails to produce schema-valid JSON on the original attempt plus two repair attempts, the pipeline stops rather than looping forever | Check the raw model response for the failure pattern (e.g. markdown fences it kept re-adding, a hallucinated `row_hash` not present in evidence, wrong severity enum value). This usually indicates a smaller/less-capable model behind that provider than the prompt was written against |
| Bedrock analysis "hangs" with no incremental output, unlike some other providers | **Bedrock streaming is not implemented** — the adapter always sends a non-streaming request and waits for the full response | Expected behavior. There's nothing to fix; the UI simply won't show token-by-token progress for Bedrock the way it might conceptually for a streaming-capable provider |
| Saved credentials are gone after clearing browser data / using a different browser or profile | Credential persistence, when opted into, is AES-GCM-encrypted `localStorage` under `ir-triage:credentials:v1` — origin- and profile-scoped, like all `localStorage` | Re-enter credentials in the new browser/profile. There is no cross-device sync by design (credentials never leave the browser except to their own provider) |
| Attempting to inspect or log a credentials object shows an error instead of the expected JSON | The anti-logging guard: `SecretCredentials` throws on `toJSON()`/`JSON.stringify()` to prevent an accidental secret leak into logs/console | This is intentional. Read individual fields directly (e.g. `creds.apiKey`) instead of serializing the whole object |

## Build (`build/build.ps1`)

| Symptom | Cause | Fix |
|---|---|---|
| Build fails at the Gates step with a Go test failure naming Hayabusa rule preparation | An earlier revision of this build embedded Hayabusa's 7 MB *live-response* bundle, whose rules ship as a single `encoded_rules.yml` file rather than the `<dir>/config` directory layout `HayabusaEngine.Prepare` requires — Hayabusa could never have run against that bundle | Current builds instead pin the separate ~3.6 MB `hayabusa-rules` tarball alongside the small live-response binary. If you've modified `build/assets.lock.json` to point at a different Hayabusa asset, confirm it has the `<dir>/config`-style rule layout, not a single encoded rules file |
| Freshly-built EXE is far smaller than the documented ~95–110 MB range (e.g. only a couple of MB) | `go:embed` only links a payload if the embedding package is actually reachable from `main`'s import graph. A `main.go` that doesn't import the packages that embed the real payloads links none of them | Confirm `client/main.go` imports the full `internal/...` tree that performs the embedding, and that the build did not silently short-circuit before compiling against the real package set |
| PE manifest verification step fails the build, reporting `requireAdministrator`/`longPathAware`/`trustInfo` not found in the compiled EXE | `scripts/gen-manifest-syso.py` did not run before `go build`, or its output `.syso` isn't in the same directory as `main.go` (`go build` only auto-links a `.syso` from the main package's own directory — not a subdirectory or a different location) | Do not reorder `build/build.ps1`'s Compile step; the manifest `.syso` must be generated before `go build` runs, in `client/`'s own directory. Check for a stale `dist/IRTriage.exe.manifest` side-car — the build removes this file specifically because a side-car manifest defeats the single-EXE requirement |
| `go test ./...` outside of `build/build.ps1` (i.e. run manually) fails to even launch the `main` package's test binary, with an elevation-related error, even though you didn't ask for a real run | The embedded PE manifest applies to the test binary too, since Go links the same `.syso` into it — Windows refuses to launch it unelevated | Export `__COMPAT_LAYER=RunAsInvoker` before running `go test` manually (this is what `scripts/go.sh` does automatically), or run the test from an elevated shell |

## Determinism / verification

| Symptom | Cause | Fix |
|---|---|---|
| Two collections against what should be identical evidence produce byte-different `timeline.csv`/`timeline.jsonl` | The timeline builder's own determinism contract (`(timestamp_utc, source, artifact, row_hash)` total order, RFC3339 with exactly 7 fractional digits, SHA-256 `row_hash` dedupe) is verified by a repeated-run test against a fixed fixture in `internal/timeline`. A real difference against real host evidence usually means the evidence itself differs between runs (e.g. a running process changed state, a new event log entry appeared) rather than non-determinism in the builder | Compare `manifest.json`'s row counts and per-artifact status between the two runs to see what actually changed on the host, rather than assuming the builder is non-deterministic |
| `--verify` or an independent hash check disagrees with `SHA256SUMS` on a file that was never modified | Check whether `output.hash_algorithms` was changed between the run that produced the archive and whatever tool is re-verifying it, or whether the file was touched by any post-processing (AV quarantine-and-restore, antivirus rewriting alternate data streams, etc.) after collection | Re-collect if the discrepancy can't be explained by a benign hash-algorithm mismatch; treat any unexplained mismatch as a chain-of-custody concern, not a display bug |
